# Memory Schema

## Purpose

This repository preserves durable personal-assistant memory as portable, auditable files. It separates durable facts, chronological records, structured source material, readable pages, and immutable raw artifacts.

The schema is designed for local/private operation, explicit provenance, mechanical validation, controlled schema evolution, and safe interaction with an automated assistant.

## Directory Layout

- `AGENTS.md`: primary policy for memory behavior, write boundaries, and durable-memory decisions.
- `CLAUDE.md`: pointer file for Claude Code.
- `WIKI_SCHEMA.md`: approved operating contract for structured memory.
- `WIKI_SCHEMA_PROPOSALS.md`: maintained proposal queue for generic schema changes.
- `facts/`: concise durable facts, preferences, goals, constraints, and other long-lived user information.
- `records/`: chronological interaction or event records that are useful for continuity but are not durable facts.
- `wiki_records/`: structured records retained for source-oriented or legacy wiki-compatible information.
- `wiki_pages/`: human-readable maintained pages derived from structured records when such pages remain useful.
- `raw/`: immutable source artifacts stored physically outside `memory/`. In the repository layout this is exposed only through `memory/raw` as a symbolic link for read access.

`raw/` is not a writable memory area. New raw artifacts must be created under the physical `raw/` tree by the application, not by the assistant through `memory/raw`.

## Memory Types

### Facts

`facts/` contains durable information expected to remain useful across future conversations.

Examples include stable preferences, explicit goals, recurring constraints, and user-provided background that is appropriate to retain.

Facts must be concise and must not contain invented details.

### Records

`records/` contains chronological or event-oriented information that may be useful for continuity but should not automatically be promoted to a durable fact.

A record may preserve context, decisions, completed actions, or notable conversation events.

### Wiki Records And Pages

`wiki_records/` and `wiki_pages/` are retained for structured source-oriented material and legacy knowledge-management content. They must not be used as a substitute for `facts/` or `records/` when the content is specifically personal assistant memory.

Existing wiki content may be maintained when required for compatibility, but new personal memory should prefer `facts/` and `records/`.

## Raw Artifacts

Raw artifacts are immutable source material such as uploaded PDFs, images, and captured conversation files.

Raw artifacts are stored under the physical `raw/` directory outside the assistant's writable memory root. `memory/raw` is a symbolic link to that directory.

The assistant must not modify, delete, rename, or replace raw artifacts. Derived text or metadata may be generated by application code beside a raw attachment when explicitly supported by the attachment-processing pipeline.

A raw-path reference should be relative to the repository root and use `raw/...`.

## Provenance

Durable memory should be traceable to its source whenever practical.

For conversation-derived memory, use the corresponding raw conversation record or record path as the provenance source.

For externally sourced knowledge retained in the memory system, use an appropriate structured source record under `wiki_records/` and reference the associated raw artifact when present.

Do not create citations or provenance claims that are not supported by an existing source.

## File Conventions

Markdown files under `facts/` and `records/` should use clear, stable names based on their subject or record date. Avoid names that depend on temporary process state.

Human-readable wiki pages under `wiki_pages/` remain Obsidian-compatible and use minimal frontmatter.

Every markdown file under `wiki_pages/` must include the required frontmatter fields defined below.

## Page Types

Allowed `page_type` values are `source_summary`, `entity`, `concept`, `synthesis`, `index`, `log`, and `questions`.

These page types apply only to `wiki_pages/` content. Personal memory facts and records do not require wiki-page frontmatter unless they are intentionally represented as wiki pages.

Readable wiki pages use minimal Obsidian-compatible frontmatter:

```yaml
---
record_id: SRC-0001
page_type: source_summary
title: Example Source
aliases: []
tags:
  - source
---
```

Allowed page frontmatter fields are only `record_id`, `page_type`, `title`, `aliases`, and `tags`.

Required page frontmatter fields are `page_type`, `title`, `aliases`, and `tags`. `record_id` is required only when a page mirrors a structured record.

## Source Records

Structured source records live under `wiki_records/sources/` as `.yaml` files.

A v1 source record uses this contract:

```yaml
record_id: SRC-0001
record_type: source
status: active
source_storage: local
raw_path: raw/SRC-0001/example.pdf
source_url:
page_path: wiki_pages/sources/SRC-0001-example-source.md
source_type: paper
source_format: pdf
title: Example Source
authors: []
added_date: 2026-05-11
processed_date:
published_date:
content_fingerprint:
arxiv_id:
doi:
bibtex_key:
```

Required source record fields are `record_id`, `record_type`, `status`, `source_storage`, `source_type`, `title`, `authors`, and `added_date`.

Optional source record fields are `duplicate_of`, `superseded_by`, `raw_path`, `source_url`, `page_path`, `source_format`, `processed_date`, `published_date`, `content_fingerprint`, `arxiv_id`, `doi`, and `bibtex_key`.

The source record field set is closed in v1. Unknown fields are invalid.

`record_type` must be `source`.

Controlled `status` values are exactly `active`, `archived`, `superseded`, and `duplicate`.

Controlled `source_storage` values are `local` and `external`.

When `source_storage` is `local`, `raw_path` must point under `raw/`.

When `source_storage` is `external`, `source_url` is required.

## Relation Records

Relation records live under `wiki_records/relations/` as `.yaml` files.

A v1 relation record uses this contract:

```yaml
record_id: REL-0001
record_type: relation
status: active
source_record_id: SRC-0001
target_record_id: SRC-0002
relation_type: cites
direction: source_to_target
evidence: []
created_date: 2026-05-16
reviewed_date:
confidence: high
```

Required relation record fields are `record_id`, `record_type`, `status`, `source_record_id`, `target_record_id`, `relation_type`, `direction`, `evidence`, `created_date`, and `confidence`.

Optional relation record field is `reviewed_date`.

The relation record field set is closed in v1. Unknown fields are invalid.

`record_type` must be `relation`.

## Durable Memory Policy

Only information that is explicitly provided by the user, directly supported by stored source material, or strongly established by the conversation may be written as durable memory.

Transient conversational details should normally remain in `records/` rather than `facts/`.

Memory must not be fabricated, inferred beyond the available evidence, or silently promoted from an uncertain statement to a durable fact.

Prefer updating an existing memory file over creating redundant files.

Do not store passwords, API keys, access tokens, private credentials, or other authentication secrets in durable memory.

New durable synthesis that materially combines multiple sources or changes the meaning of stored knowledge requires human approval.

## Query Workflow

Answer from relevant existing memory first when useful. Consult `facts/` for durable context and `records/` for recent or chronological context. Consult `wiki_records/` and `wiki_pages/` when source-oriented knowledge or legacy wiki material is relevant.

Do not modify memory merely because a file was read. Write only when there is a concrete durable-memory benefit.

## Ingest Workflow

For a Discord attachment or conversation event:

1. The application stores the raw source under physical `raw/`.
2. The application may create derived attachment caches such as extracted text under the raw attachment directory.
3. The application writes a conversation record under `raw/discord/`.
4. Relevant durable information may be promoted to `facts/` or `records/` according to the memory policy.
5. Provenance should point back to the corresponding raw record or source record whenever practical.

The assistant must not rewrite or delete the original raw artifact during this workflow.

## Lint Workflow

Mechanical drift may be fixed automatically when the intended meaning is unchanged.

Semantic, schema, destructive, archival, deletion, relation, and durable-synthesis changes require human approval.

Rendering managed wiki sections from approved structured records is mechanical work. Creating or changing the meaning of structured relations is semantic work.

## Review Policy

Human approval is required for:

- schema changes;
- new exception-like rules;
- semantic rewrites;
- duplicate merges;
- superseding or archiving records;
- deletion of durable memory;
- creation or semantic modification of relation records;
- relation vocabulary changes;
- new durable synthesis that materially changes existing meaning.

Schema changes must be proposed in `WIKI_SCHEMA_PROPOSALS.md` before approval.

## Naming Conventions

Use explicit short field names.

Universal identifiers such as `record_id`, `record_type`, `source_type`, and `source_format` are preferred where they are precise.

Source records use IDs such as `SRC-0001`.

Relation records use IDs such as `REL-0001`.

Dates use `YYYY-MM-DD`.

## Schema Evolution

Top-level schema sections are fixed in v1 unless a human-approved schema proposal changes them.

Schema rules and subsections must remain generic. Entry-specific exceptions do not belong in the schema.

If an agent encounters an entry-specific exception request, it must route the request to human review as a question or schema proposal instead of adding a one-off schema rule.
